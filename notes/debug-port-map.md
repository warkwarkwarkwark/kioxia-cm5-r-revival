
Hardware findings on the HPE VO015360KWUEE (Toshiba KCM5XRUG15T3, controller TC58NC1033GTC), probed 2026-11-13 with a multimeter and an FT232 listener. See [[hpe-15tb-firmware-analysis-result]] and [[hpe-15tb-risk-stance]].

- Main board does not power its logic without the daughterboard mated (Winbond VCC read 0V alone).
- Boot flash: Winbond W25Q80EW, 1 MB SPI NOR, **1.8V part**, SOIC-8 on the main-board face the daughterboard covers. Dumped 2026-11-19, see the section below.
- 8-hole header (pin 1 at the silkscreen triangle), no ground pin: pins 1-4 = 0V; pin 5 = 5V (high impedance); pin 6 = 1.8V steady; pin 7 = 1.8V; **pin 8 = 12V input rail**. Pin 7 was captured at 115200/921600/3M baud: only power-on glitches, not serial data.
- Corner footprint by the data-matrix sticker (exposed by a chassis window), 8 copper test points at ~1 mm pitch, counted from the sticker end: TP1 = 1.8V (suspected drive TX), TP2 = 1.8V steady (suspected RX), TP3 = ground, TP4-8 = 0V. TP1 was **silent during boot** at 115200 (only isolated glitch bytes on touch/power events). Sending to TP2 has not been tried; it needs a 3.3V→1.8V drop on the adapter TX.
- USB adapter ground is already common with the drive through the PC, so no separate ground lead is needed for listening.

**Why:** avoids re-probing; the 12V pin next to 1.8V logic on the header is a real hazard.
**How to apply:** treat the roles of TP1/TP2 as unconfirmed guesses until the drive is seen to transmit or respond.

## Console gating, from disassembly (2026-11-19, spot-checked)

Correction: the main image is linked at **VA = file offset + 0x40** (not 0). The flash holds three images: 'F' front-end boot kernel with the monitor (file 0x140, load 0x180, size 0x22000), 'K' NAND-manager CPU code (file 0x22180, load 0x50000000), 'M' (file 0x2D430, load 0x80C20000). VA-correct disassembly lives in the session scratchpad only (rebuild with llvm-objdump --triple=thumbv7r if needed).

- **Unlock: send four consecutive ESC (0x1B) bytes.** Locked handler at VA 0x18896 counts ESCs at RAM 0x40400+0x110; on the 4th it installs the full handler and prints `[[\rOK!`. Prompt is `>`. Commands must start with `/`, CR executes. No password.
- **Baud rate/UART base are NOT in the dump**: printf/getc/monitor core are in the SoC mask ROM at 0x2040xxxx (printf 0x204072D0, getc 0x20404914). Baud must be found by scanning: send 4xESC at each rate and look for `OK!`.
- Image F prints nothing on a normal boot (all printf calls are in commands/asserts), which matches the silent TX.
- **This drive is in restricted mode**: lock flag (RAM 0x49CC0) derives from DDP record 0x13 at flash 0x626A0 (word0 = 2, magic 0x9F52B87D at 0x627FC; record also holds serial `<INTERNAL-SERIAL>…`). Flag is 0 only if magic present and word0 == 1, or both blank. DDP ("DI  " block at flash 0x60000-0x64FFF) is integrity-checked with a ROM algorithm (check word at 0x64FFC); a failed check makes the record read as blank (flag 0) but other side effects are unknown.
- Whitelist while locked: `/m /mm /wb /ww /wl /rate /psave /reg /lap /um /pm /fpsave /ymsend`; writes limited to addresses 0x5xxxxxxx or 0x2461xxxx. Memory **read** is allowed, so the mask ROM and RAM should be dumpable.
- Destructive when unlocked: `/spi 1,2,4,5,6,8` (erase/write flash), `/phyreg 1,3,8`, `/dram x,y,z`.
- "Factory Mode" is a RAM flag (0x41000) set by vendor NVMe admin opcode 0xFC with payload string "FactEnb"/"FactDsb" (same handler knows "FlErase", "DrErase", "SeErase", "WtPrtct"); it does not affect the console lock.
- Bus Pirate UART mode: IO4 = TX, IO5 = RX.

## Mask ROM analysis (2026-11-19, key points spot-checked)

- **ROM command table** at 0x20405CCC (12 entries): `/m addr,count[,width]` (read), `/mm addr` (128-byte hex+ASCII dump, read only; SPACE pages on), `/wb /ww /wl addr,value` (write), `/wf addr,count,value` (fill), `/rate index`, `/pload addr` (XMODEM receive into RAM), `/psave addr,len` (XMODEM send; read only, stalls firmware, wants NAK first, 128-byte blocks with 8-bit sum), `/func addr` (call address), `/sf` (SPI flash: **`/sf 1` chip-erases immediately with no confirmation**, `/sf 2,dst,src,cnt` program, `/sf 8,n` block erase, `/sf 9` status). `/pm /um /reg /lap /spi` are image F's. `/fpsave` and `/ymsend` have no handler in ROM or flash.
- Parser: hex only, max 8 chars, comma-separated, no spaces after commas, up to 4 args. SPACE or BACKSPACE at a fresh prompt repeats the previous line; never type a stray space after an `/sf` command.
- **While locked nothing reaches `/func /pload /wf /sf`**: whitelist is an exact strcmp of the command word. Allowed writes (`/wb /ww /wl`) only to 0x5xxxxxxx (includes image K's RAM at 0x50000000) or 0x2461xxxx.
- UART at 0x20412000 (16550-style), divisor 27 on a 50 MHz clock. `/rate` takes an index: 2 = 57600, 3 = 115200, 4 = 781250 (exact), 5 ≈ 1.04 M (printed as 1152000), 1 and 6 are risky. Change takes effect after a delay; not persistent.
- **DDP check is a plain additive checksum**: the 0x1400 little-endian words of flash 0x60000-0x64FFF must sum to 0 (check word at 0x64FFC; verified: sum is 0, stored word 0x39D96849). The DDP is outside the range covered by the boot check below.
- **Boot check of images F/K/M**: ROM copies flash 0..0x2F660 to RAM 0x40 and has a hardware block (0x23001910/14) compare against a 32-byte value at flash 0x2F640. Not plain SHA-256; presumably keyed. Assume modified code images will fail with "[SFROM] BOOT SUM ERR". K and M additionally have additive sums of 0.
- On boot failure the ROM prints the error repeatedly and offers its **unrestricted** monitor after ESC x4, but only if [0x2300150C] == 0 and [0x23001510] == 0 (values on this drive not yet read). Boot-mode register 0x24783020 and strap 0x24783400 select alternate boot paths (mode 1 boots from SPI with only an additive sum).
- ROM working disassembly was in the session scratchpad (`rt.asm`); rebuild with llvm-objcopy `--change-addresses=0x20400000` + llvm-objdump `--triple=thumbv7r`.
- Context: this drive is the "dead" one whose host reads fail (see [[hpe-15tb-firmware-analysis-result]]); the blocked F commands `/kbs`, `/sys`, `/felog`, `/festat`, `/adc` are the ones that would show its boot/fault state, and their data can also be read from RAM with `/m`.

## Unlock planning (2026-11-19, rule and arithmetic spot-checked)

- **Local lock rule (identical code in boot image F 0x1C538 and main firmware 0x80B47728) looks at only two words of record 0x13**: if word +0x15C == 0x9F52B87D, unlocked only when word +0 == 1; otherwise unlocked only when both words are 0xFFFFFFFF or both are 0. Nothing else in the record is examined by the main CPU.
- **No-erase edit that satisfies it**: program record 0x13 (flash 0x626A0-0x6281F) to all zero and program the unused word at flash 0x62820 (currently 0xFFFFFFFF, outside every directory record) to **0x3AD117D0**. Verified by computation: only clears bits (385 bytes change), DDP sum stays 0, check word at 0x64FFC untouched. Restoring the original needs an erase of sector 0x62000 (or the 64K block) and reprogramming from the backup.
- **Outcome is certain only for the boot stage**: image F takes the local rule as final (its security-exchange code is unreferenced). **In the main firmware the local result is overridden** by a later exchange with a separate security processor (opcode 0x10000 over the mailbox 0x20205180/0x202051B0): flag = 0 only if its response word's low 16 bits == 1. That processor's code is in no dump, so its verdict for a zeroed record is unknown. It is handed a pointer to the record buffer and can request a save (bit 3 of 0x51024 -> firmware rewrites record 0x13 to flash), and a firmware path exists that blanks record 0x13 to all-FF. A "SEC3" structure in the system area (0x9237A850) holds the same ID string, so the security side has its own copy.
- Record 0x13 is read straight from flash on each use (not RAM-cached). DI header +4 is a big-endian write counter (currently 0x38): compare across boots to see whether the firmware rewrote the block. Any firmware rewrite recomputes the checksum.
- "DI2 " at flash 0x70000 is NAND parameter tables (length 0x20000, last word = plain sum), unrelated to the lock.
- What flag 0 enables besides the full monitor: vendor NVMe memory-access commands (boot stage), "DrErase"/"SeErase" keyword commands (boot stage, also need factory mode), and in the main firmware it skips the firmware-download code-compatibility check (signature step still runs) and un-gates some security sub-commands. No boot/NAND/data-path test of the flag was found in dumped code.
- Still worth reading on the console before any write: 0x80D29400-0x80D2A1FF (record buffer + security request/response buffers), 0x51018-0x5102F, 0x80B4C000-0x80B4CC3F, 0x80B20000-0x80B2FFFF, 0x812AE9C4 + 0x812AF0B8, 0x923A0000-0x9245CFFF.

## ROOT CAUSE (2026-11-20, from the scan trace + BE disassembly; patch bytes spot-checked)

**The BE's persistence journal ends without a shutdown commit record, and the firmware has no fallback.** The scan finds its root (list id 0xAA5, pos 0x1AC), both journal ends (previous id 0x893 ends 0x601; current id 0x1A38 ends 0x21C; four copies unanimous), loads the base snapshot (284 chunks, list id 0x563F), replays all 0x21D journal pages with status 0 and no retries, and then fails only because `[0x531D0+0x98C]` (set by record 0x8000007 = "dump of all sets committed", written at clean shutdown; cleared by 0x1000002 = "boot complete") is 0. I.e. after its last successful boot the drive never completed a shutdown/power-loss dump: an unsafe power loss with no completed PLP dump, or a BE hang followed by a power cycle. Nothing on NAND is unreadable. In TROUBLE mode persistence writes nothing, which is why nothing has changed since (counters frozen at the last base snapshot).

**After any revival the drive must get a clean NVMe shutdown (CC.SHN) and finish its dump before power is removed, or it returns to this state.**
